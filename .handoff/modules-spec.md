# ReCasaOS modules: install a module from the installer and from the dashboard — binding spec

Owner's decisions (2026-10-16): take the virtual machine module of Vinz2168 into the organisation (he transfers `CasaOS-VirtManagement`; asked on ReCasaOS/CasaOS#18) and offer it for installation from the dashboard; the install lives in ONE assistant with a catalogue pinned by each ReCasaOS release (nothing from the network runs as code). The public contract is `docs/modules.md` of CasaOS-Install (merged, main ba41c26): read it first; this file is how it gets built and where it is made precise or changed.

## 0. One change to the contract: the assistant is a subcommand of the core, not a shell script
`docs/modules.md` says `casaos-module` is a small shell tool. DECISION: it is a **subcommand of the core binary**, `casaos module <list|plan|install|remove|status>` (dispatched in `main.go` before `flag.Parse`, as the engine's `os-upgrade-run` is), for these reasons: the box has no `jq` and JSON in bash is where the bugs would be; sha256, tar extraction with path rules, the manifest and catalogue validation and every failure path become Go code that is unit-tested on Windows; the core release is already verified by the installer, so no new file needs its own pinned digest; and the core's API uses the same code in-process for `plan` and through a transient unit for `install` and `remove`. `install.sh --module <name>` calls `/usr/bin/casaos module install <name>` once ReCasaOS is installed and running. The doc is corrected in the first slice (S1). Everything else of the contract stays.

## 1. Repos, branches, rules
Core `CasaOS` (branch `feat/modules` from current `inkly/main`); installer `rel0524` (branch `feat/modules-installer`, from `origin/main`); UI `CasaOS-UI` (branch `feat/modules-page`). Rules for every implementer: local commits only (NO push/PR/merge/tag/dispatch), NO Co-Authored-By trailer or Claude footer, nothing in committed text that cites review rounds, specs, rulings or scratchpad paths, test-first with mutation checks, CRLF worktree / LF blobs, shell under dash, `go test -race` CI-only on Windows, short plain structured answers. The pull request check refuses attribution lines in commits and descriptions.

## 2. What is on a box
| Path | Written by | Content |
|---|---|---|
| `/usr/share/casaos/modules/catalogue.json` | `install.sh` (a release asset, digest pinned in the script) | the catalogue of this release |
| `/etc/casaos/modules/<name>.json` | `casaos module install` | the manifest copied from the archive (root, 0644) |
| `/var/lib/casaos/modules/<name>.files` | install | one absolute path per line: every file the install put down (root, 0644); remove deletes exactly these |
| `/var/lib/casaos/modules/tmp/` | install | download and unpack area, emptied on every exit |
| `/var/log/casaos/module-<name>.log` | install and remove | the steps, one marker line each |

## 3. Manifest rules (schema 1, strict where it matters)
A manifest is rejected, and the module is not installable or is shown as broken, unless: `schema` is 1; `name` matches `^[a-z][a-z0-9-]{0,31}$` and equals the file name without `.json`; `unit` matches `^[A-Za-z0-9:_.@-]{1,64}\.service$`; `gateway_route` matches `^/v[0-9]{1,2}/[a-z0-9_]{1,40}$`; every package name matches `^[a-z0-9][a-z0-9+.-]{0,63}$` (at most 40 in all); `min_recasaos` is `N.N.N`; each `os` is `^(debian|ubuntu):[0-9]{1,2}(\.[0-9]{1,2})?$`; `title` is 1 to 60 printable characters and `description` at most 300 (control characters refused, they are shown in the dashboard as text). Unknown fields are ignored (forward compatible) except that an unknown `schema` is refused. `os_upgrade` is NOT read in this work (the field is ignored if present).

## 4. Catalogue rules
Same schema as `docs/modules.md`. Validated on read: every `url` is exactly `https://github.com/ReCasaOS/<component>/releases/download/<tag>/<archive>` with `<component>` equal to the entry's component (the repository name pinned in the entry), `<tag>` matching `^v[0-9]+\.[0-9]+\.[0-9]+$`, `<archive>` matching `^linux-(amd64|arm64)-casaos-[a-z-]+-v[0-9.]+\.tar\.gz$`; `sha256` is 64 lower-case hex; `tier` is `core` or `community`; `commit` is 40 hex. A catalogue that does not parse leaves the module list empty and says so (never a partial list).

## 5. The commands (S1 and S2)
Global: `--json` is the default for `list`, `plan` and `status`; every command is read-only except `install` and `remove`, which need root and refuse otherwise (`not_root`). Exit codes: 0 done, 2 refused (a code, nothing changed), 3 failed (rolled back as said). Output of `plan`, `list`, `status` is JSON on stdout, one object, no other text.
- `casaos module list`: `{catalogue: {ok, error?}, modules: [{name, title, description, tier, tag, installed: {version}|null, system: {supported, reasons[]}, broken?: reason}]}`: catalogue entries joined with `/etc/casaos/modules/*.json` (an installed module that is no longer in the catalogue is listed with `catalogue:false`).
- `casaos module plan <name>`: `{name, tag, tier, checks:[{code, ok, detail}], refused: code|null, packages:{to_install[], to_upgrade[], download_bytes, extra_bytes, known}, archive:{url, bytes?}, plan_id}` where the checks are, in this order: `catalogue` (entry exists), `not_root`... no: `plan` is allowed unprivileged (read-only) and reports `not_root` as a check only for install; `os` (the box's `ID:VERSION_ID` in the manifest's list), `arch` (amd64 or arm64 and an asset for it), `recasaos` (core version >= `min_recasaos`), `already_installed`, `foreign_unit` (a unit file of that name exists that this module's `.files` does not own), `busy` (another package manager runs: the dpkg lock and the same units the readiness report looks at; the OS-upgrade engine's busy file `/var/lib/casaos/os-upgrade/busy` read fail-closed), `disk` (archive x 3 + the apt download + the apt extra, on `/var/lib/casaos/modules/tmp`'s and `/usr`'s file systems; the factors in one table), `apt` (apt-get exists). The apt numbers come from `apt-get -s install --no-install-recommends <packages>` in a sandbox of the same kind as the OS plan's: reuse its allow-list and runner (`pkg/osplan` exports what is needed: a small export file in that package; never copy its parsing). `plan_id` = `m1-` + first 32 hex of the SHA-256 of {name, tag, sha256 of the archive for this arch, sorted packages to install, the box's os id and version}.
- `casaos module install <name> [--yes] [--plan-id <id>]`: re-runs the plan; refuses with its `refused` code unless every check is ok; with `--plan-id` it refuses `plan_changed` when the id differs; without `--yes` and without a terminal it refuses `confirmation_needed`; with a terminal it prints the plan and asks. Then the steps (a marker line in the log and on stdout for each: `CASAOS_MODULE_STEP <nonce|-> <name> <step> <begin|done|failed> <ts>`; the nonce is `$CASAOS_MODULE_NONCE` when set, as the core passes it, else `-`): `packages` (`apt-get install -y -q --no-install-recommends` with the Docker update's apt options and `DEBIAN_FRONTEND=noninteractive`, timeout 30 min, a held package refuses `held_package` before it starts); `download` (https, redirects only to `github.com` and `objects.githubusercontent.com`, size limit 200 MiB, 3 tries); `verify` (sha256 against the catalogue: a mismatch deletes the file and stops, `checksum_mismatch`); `unpack` (see 6); `units` (`daemon-reload`); `manifest` (copied from the archive's `module.json`, validated again, the `name` must equal the catalogue's, written atomically); `start` (`systemctl enable --now <unit>`); `route` (waits up to 60 s until the gateway answers on `gateway_route`: any HTTP status except 502/503/504/connection refused counts as answering, through the gateway's own port read from `/etc/casaos/gateway.ini`); `done`. A failure at any step rolls back what the steps after `packages` did (stops and disables the unit, deletes the files of the `.files` list written so far and the manifest, `daemon-reload`), keeps the apt packages and says so in the last line (`kept_packages: ...`), and exits 3 with the failing step named.
- `casaos module remove <name> [--yes]`: refuses `not_installed`, `busy`, `confirmation_needed` as above; stops and disables the unit, deletes exactly the files of `<name>.files` that still exist and are not owned by another module's list, removes the manifest and the list, `daemon-reload`. It never purges packages and never touches data; the last lines say what is left (for `virt`: `/DATA/VM`, the libvirt network and pool, the machines, the packages) and how to remove them by hand (printed commands, not run).
- `casaos module status [name]`: `{name, installed, version, unit:{active, enabled}, route:{answers}}` (read-only).
Idempotence: a second `install` of an installed module refuses `already_installed`; a `remove` of a module whose files are partly gone completes; nothing in `plan` or `list` writes anything on the box (an invariance test).

## 6. Unpacking rules (the only place where archive content reaches the file system)
The archive is the module's release archive (already verified by sha256). Allowed entries: regular files, directories and symlinks. Every entry path must start with `build/sysroot/` or be exactly `module.json`, `LICENSE`, `NOTICE`; no absolute path, no `..` element, no hard links, no device or fifo, no symlink whose target is absolute or leaves the entry's directory, total size <= 400 MiB, at most 5000 entries. Destination allow-list (relative to the sysroot): `usr/bin/`, `usr/lib/systemd/system/`, `lib/systemd/system/`, `etc/casaos/`, `usr/share/casaos/`, `var/lib/casaos/`: any other destination refuses `unpack_path` and nothing is written. A destination file that exists and is not in this module's own earlier `.files` is NOT overwritten: the install refuses `file_exists` before writing anything (checked for the whole archive first), except under `etc/casaos/` where an existing config is kept and the new one is written beside it with the suffix `.sample` only if the archive's name already ends in `.sample`. Modes are the archive's, with the setuid, setgid and sticky bits cleared and group/other write cleared. Written atomically (temp name and rename in the same directory), in an order that puts the unit last.

## 7. The core API and the transient unit (S3)
The core's endpoints, all under the JWT group like the other `/v1/sys` ones, POSTs behind `headerTokenOnly`: `GET /v1/sys/modules` (the `list` object), `POST /v1/sys/modules/{name}/plan` (the `plan` object, run in-process, bounded 60 s), `POST /v1/sys/modules/{name}/install` body `{plan_id}` (202 with the status, or 409 with `data.error_code`), `POST /v1/sys/modules/{name}/remove`, `GET /v1/sys/modules/{name}/status` (the state of the install job and `status`). One module job at a time (refusal `busy`); refused while the OS-upgrade engine holds the machine or a package update runs (`maintenanceBusy`, fail closed). The install runs as a transient unit `casaos-module-<name>.service` (`systemd-run --quiet --no-block --collect --unit=... --property=Type=exec --setenv=CASAOS_MODULE_NONCE=<32 hex> ... /usr/bin/casaos module install <name> --yes --plan-id <id>`; same closed argument allow-list as the Docker update unit: no dollar sign, no percent sign, name and id validated), the job state is reduced from the log's marker lines (nonce checked) and the unit's state with the rules `idle running succeeded failed(step, reason) interrupted` (an unit that disappeared with no `done` marker is `interrupted` after 30 s; the core never restarts it by itself). It reuses the marker and nonce helpers of `pkg/dockerpkg`. No state file beyond the log. The status carries the last 20 sanitised lines of the log (the plan's sanitiser). Alerts: none in this work.

## 8. The dashboard page (S4)
A *Modules* entry in the settings, a page listing `GET /v1/sys/modules`: per module the title, description, tier badge (`community`: a short sentence), installed version, whether this system supports it (the reasons if not, by code, translated), and a button. *Install* asks for the plan (spinner), then shows it in a confirmation window: the packages and the download in readable units, the system check results, the tier sentence, and for `virt` nothing hard-coded: what the module declares is all there is (a `description`), the security note about USB passthrough and firewall chains is part of the module's `description` in its manifest, which the dashboard shows as text. Confirm calls install and the page follows the job (polling that survives errors, one request at a time), then says done and that the module's card appears; a failure shows the step and its reason by code, and what was kept. *Remove* asks for a confirmation that says what stays. Text rules as the plan section of the OS window: everything from the core is rendered as text, never HTML; English and French strings by code; accessibility basics; narrow screens. The module's own card still appears only where the service answers (today's behaviour), nothing there changes.

## 9. The installer (S5, CasaOS-Install)
`scripts/build-release-bundle.sh` writes the catalogue as a release asset `modules-catalogue-<tag>.json` from `release/modules.env` (new: `MODULE_VIRT_TAG`, `MODULE_VIRT_COMMIT`, `MODULE_VIRT_COMPONENT=CasaOS-VirtManagement`, `MODULE_VIRT_TIER=community`, an `OWNER` override for a module that is not yet under the organisation) and from the `checksums.txt` of the module's release (fetched exactly as the components' are), the manifest's name and title read from the archive's `module.json`, and writes its digest into `install.sh` (`__CASAOS_MODULE_CATALOGUE_SHA256__`, verified like the others, a tampered or missing file stops the install of the catalogue ONLY, not ReCasaOS). `install.sh` places it at `/usr/share/casaos/modules/catalogue.json` with the rest of the install and on every update, and gains `--module <name>` (repeatable; the name validated `^[a-z][a-z0-9-]{0,31}$`; unknown option values refused before anything is changed): after ReCasaOS is installed and its services run, for each module it runs `casaos module install <name> --yes`; a failure prints the step and the reason and the install carries on: the exit status of the installer does not change. Tests in the style of `scripts/test-install-dependencies.sh` and `scripts/test-install-banner.sh` (a shell harness with stand-in commands): the option's parsing, the failure that does not fail the install, the catalogue placement and the digest check. `release.yml` publishes the new asset. The modules list of a bundle can be empty (no `release/modules.env` entries): then no catalogue asset is built and the core says `catalogue: {ok:false, error:"none"}`.

## 10. The QEMU proof (S6, CasaOS-Install `module-proof.yml`, dispatch-only, in the style of `os-plan-proof`)
Legs `d12` (Debian 12) and `u24` (Ubuntu 24.04), amd64, a release `tag` input that carries the catalogue. On each guest: install ReCasaOS from that release (the harness reuses the QEMU boot and the INVALID RUN versus FAIL discipline of the other proofs); (a) `casaos module list` and `plan virt`: the verdicts and the packages; (b) `casaos module install virt --yes` with `/etc/casaos/virt-management.conf` set to libvirt's test driver (`[libvirt] URI = test:///default`) before the start, so that no KVM is needed; the steps in order; the gateway answers on `/v2/virt_management`; with a token from the box's own login the `GET /v2/virt_management/host` says libvirt is there; the VM card condition of the dashboard (the same request the UI makes) is true; (c) the API: `GET /v1/sys/modules` shows it installed, a second install is refused `already_installed`, `plan` with a changed catalogue entry is `plan_changed`; (d) the dirty matrix, each with its undo: a corrupted archive (the harness serves a local copy through a file URL in a test-only catalogue: `plan` and `install` honour `CASAOS_MODULE_CATALOGUE` ONLY when `CASAOS_MODULE_TEST=1` is set, which the shipped unit never sets) gives `checksum_mismatch` with nothing left; an archive with `../` entries gives `unpack_path`; a pre-existing unit file of the same name gives `foreign_unit`; the dpkg lock held gives `busy`; a low disk gives `disk_short`; a kill of the unit mid-install leaves `interrupted` and a rollback by `remove`; (e) `remove`: the files of the list are gone, the manifest is gone, the packages and `/DATA/VM` stay and the last lines say so; (f) invariance of everything the module does not own: a before/after hash of `/etc`, `/var/lib/dpkg` is expected to change ONLY by the module's packages, the module's files and the listed state files, and nothing else of `/etc/casaos` changes. Report: PASS, FAIL, INVALID RUN, NOT TESTABLE with the reason; exit 1 on FAIL or INVALID.

## 12. What the first release will not do
No module update path other than a new ReCasaOS release carrying a newer catalogue entry; no uninstall of packages; no `os_upgrade`; no module dependencies; no module signing beyond the pinned sha256; the `virt` module is shipped as `community` and its security surface is Vinz's and ours to review once more in its own repository after the transfer.
